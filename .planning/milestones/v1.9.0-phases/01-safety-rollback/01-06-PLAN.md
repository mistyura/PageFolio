  <action>
Task 0 で option-a が確定した前提で、`delete` と `delete_redo` の 2 op に限定して蓄積方式を end-to-end で通す。この 2 op だけで「新しい state キーの導入」「`_apply_inverse` の役割縮小」「mutation ループでの蓄積」「`_restore_partial_error` での引き継ぎ」「所有権移譲」「`_dispose_state` の解放対象拡張」という設計要素がすべて揃うため、ここが成立すれば残り 5 op は同型展開になる。**残り 5 op（page_edit / insert_undo / insert_redo / merge_resize / merge_resize_undo）は本タスクでは変更しない**（Task 2・Task 3 で扱う）。

(1) state の内部キー `_pending_inverse` を導入する。値は `(page_index, blob_or_None)` タプルのリストで、「これまでの試行で実際に適用できたページ分の逆デルタエントリ」を表す。通常の `_save_undo` 由来の state には現れず、部分失敗を経由した `remaining_state` にのみ現れる。

(2) `FileOpsMixin` へ `_merge_pending_inverse(self, state, applied)` を追加する。引数 `applied` は「今回の `_restore_state` 呼び出しで実際に適用できたページ分の逆デルタエントリのリスト」。処理は、`state` から `_pending_inverse` を **pop**（取り出して削除）し、`applied` と連結し、page_index の昇順にソートして返す。pop であることが重要で、これにより「蓄積エントリの Blob 所有権が state から返り値（＝これから inverse["data"] になるリスト）へ移った」ことを表現する。所有権が移った後に `_dispose_state(state)` が呼ばれても、既に inverse が握っている Blob を解放してしまう二重解放は起きない。

(3) `_restore_partial_error` のシグネチャへ第 4 引数 `pending_inverse=None` を追加する。`None` 以外が渡された場合は `remaining["_pending_inverse"]` をその値で上書きする。`None` の場合は `remaining = dict(state)` によって前回までの蓄積がそのまま引き継がれる（この既定挙動は変えない）。呼び出し側は必ず「前回までの蓄積 + 今回適用できた分」を合流させた完全なリストを渡す。

(4) `_apply_inverse` の `delete` 分岐と `delete_redo` 分岐から、`inv["data"]` の構築を取り除く。`inv["op"]`（それぞれ `"delete_redo"` と `"delete"`）の決定と、`current_page` / `selected_pages` の記録だけを担当させる。`inv` に `data` キーを置かないまま返し、`_restore_state` 側が mutation 後に確定させる。`_apply_inverse` の他の op（rotate / crop / move / duplicate / duplicate_undo / bulk_move / bulk_crop / insert / merge / merge_undo / page_edit / insert_undo / insert_redo / merge_resize / merge_resize_undo）は本タスクでは一切変更しない。
