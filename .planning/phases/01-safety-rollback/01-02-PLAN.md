<objective>
OCR プロバイダが `off` のとき、通常 OCR・バッチ OCR・プラグイン登録プロバイダのいずれの経路からも OCR 実行に入れないようにする。現状の `build_provider` は `("lmstudio", "", "off")` を同列に扱い、`off` を LM Studio として動作させてしまう。D-06 に従い `off` のみを専用例外で拒否し（空文字は後方互換のため LM Studio 扱いを維持）、D-04/D-05 でバッチOCR メニュー項目を入口で disabled 化し、D-07 で実行開始時の二重ガードを敷く。

Purpose: OCR OFF は「外部送信とコストをゼロにする」という安全設定であり、ここに穴があるとユーザーが無効化したはずの状態でページ画像がクラウド API へ送信される（high 深刻度の情報漏洩）。Phase 2（OpenAI 追加）はこの契約の上に載るため、Phase 1 の完了が前提条件になっている。
Output: `OCRDisabledError` 例外、`build_provider` の `off` 分離、全呼び出し元のガード、バッチOCR メニューの活性制御、i18n 2 キー、回帰テスト群。
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ローカルの PDF ページ画像 → クラウド OCR API（Claude / Gemini / RunPod） | base64 化したページ画像が https で外部へ送信される境界。OCR OFF はこの境界を完全に閉じる設定であり、穴があれば直接の情報漏洩になる |
| 設定値 `ocr_provider` → OCRProvider インスタンス生成 | `build_provider` が唯一の正規ファクトリであるべき境界。ここを迂回する分岐（`ocr_dialog.py` の直接構築）が信頼境界の抜け道になる |
| プラグイン登録プロバイダ → OCR 実行経路 | `plugin_manager` 経由で登録された外部プロバイダも同じ OFF ガードに従わなければならない |
