# Phase 5: 設定読込・保存失敗の通知 - Context

**Gathered:** 2026-10-22
**Status:** Ready for planning

<domain>
## Phase Boundary

設定ファイル `pagefolio_settings.json` の読込失敗・保存失敗を利用者が正しく認識できるようにし、元の設定ファイルと編集操作を失わないようにする。

対象要件は **V110-CFG-01〜04**。新しい設定項目や設定 UI の追加は含まない。起動排他・復帰通知（Phase 4）と配布・版番号同期（Phase 6）は対象外。

</domain>

<decisions>
## Implementation Decisions

### 読込失敗の表示（V110-CFG-01）

- **D-01:** 読込失敗の通知は **非モーダルのトースト** で出す。画面構築後に表示し、編集操作を止めない。
- **D-02:** 初回の設定ファイル不存在は **警告なし** で既定値から起動する。
- **D-03:** 読込失敗は **JSON 破損** と **読取不能（権限・ロック等の OSError）** を区別する。両者とも通知するが、文言を分ける。
- **D-04:** 読込失敗の通知文言は「保存済みの設定を読めず既定値で起動した」旨を伝える。技術的な詳細（例外文字列・パス）は通常表示に含めない（Phase 4 D-09 と同方針）。
- **D-05:** 読込失敗の通知は **セッション中 1 回** だけ出す（D-11 参照）。

### 保存失敗の表示（V110-CFG-02）

- **D-06:** 保存失敗は **非モーダルのトースト** で通知する。ダイアログは使わない。
- **D-07:** 保存失敗時の文言は「保存に失敗しました。今回の変更は次回起動に残りません」の趣旨を含める。「保存しました」などの成功表示は、失敗時に出さない（成功表示への誤誘導を防ぐ）。
- **D-08:** 保存失敗時は **画面上のメモリ値を維持** する。巻き戻さない。次回起動には残らないことを通知で示す。
- **D-09:** 保存失敗は **毎回通知** する（D-11 の 1 回制限の対象外）。利用者が変更が残っていないことを毎回認識できるようにするため。

### 既存ファイルの保護（V110-CFG-03）

- **D-10:** 読込失敗（破損・読取不能）の後、既定値で **自動保存しない**。
- **D-11:** 破損ファイルの **退避コピー（.bak 等）は作らない**。
- **D-12:** 保存途中で失敗した場合（一時ファイル `pagefolio_settings.json.tmp` の書込中の失敗）は、**一時ファイルを削除** し、元ファイルを維持する。
- **D-13:** 破損ファイルの上で利用者が設定を変更して明示的に保存した場合は **上書きを許容** する。上書き前の確認ダイアログは出さない。
- **D-14（派生決定）:** D-10 の「自動保存しない」は、終了時のウィンドウ状態保存（`_save_window_state` によるジオメトリ・サッシ位置・編集モードの保存）にも適用する。読込失敗の状態では、利用者が設定を変更していない終了時の保存で破損ファイルを上書きしない。
  - **注:** この項目は利用者の個別回答から導いた派生決定であり、明示的な回答ではない。計画時に影響範囲を確認すること（下記「Claude's Discretion」参照）。

### 通知の集約と連打防止（V110-CFG-04）

- **D-15:** 読込失敗の通知は **セッション中 1 回** だけ表示する。
- **D-16:** 保存失敗の通知は **毎回** 表示する。連続する保存失敗でも、それぞれ通知が残るようにする。
- **D-17:** 画面再構築（`_rebuild_ui`、言語切替など）の際、**まだ表示中・未消化の通知は再表示** する。通知の状態は App 側で保持し、再構築で消えないようにする。
- **D-18:** 通知は **非モーダル** のため、ダイアログの連打は発生させない（D-06 と整合）。通知の重複表示で編集操作を妨げないこと。

### 2026-10-22 レビュー後のユーザー確定回答

- **D-19:** 終了時保存失敗は「最初の終了を止めて通知し、次の終了操作では保存せず終了する」。既存のDocument終了確認は維持する。確認でNoなら保存を試さず、以前の終了保存失敗flagも維持する。YesまたはDocumentなしで初めて保存を試し、初回失敗では編集・排他を保持する。次の独立した終了は保存を省略し、Document確認がYesなら閉じる。明示保存成功でflagを解除する。追加の承認checkpointは不要。
- **D-20:** 起動時unreadableは原本保護を維持し、再起動して正常に読めるまで保存しない。D-13の無確認上書き許可はcorruptだけに適用する。明示操作ではメモリ値を保持し、ディスクI/Oを行わず未保存を毎回通知する。終了時の自動保存抑止は通知を増やさず、D-19の失敗flagを立てず、既存確認を経て終了できる。
- **D-21:** 同じエラーが続いても各失敗を保持し、通知は一つずつ順番に表示する。1イベントの可視時間は10秒で、手動で閉じることもできる。勝手な統合・件数表示への合併・破棄は行わない。「集約」は同時表示を1件にする意味。100件なら可視時間の合計が最大1000秒になり、モーダルや既存PDF/印刷通知による待機時間は別に加わるトレードオフを受容する。

### 2026-10-23 条件付き実装再開のユーザー承認

- **D-22:** owner_missing・DEP-05の原因を未解決のまま残しても、一次生存/編集画面1つの検証、通知前景イベント監査、対象3回連続成功、現在差分の単一全件成功とRuff/AST成功を満たせばPhase 5実装を再開できる。出荷承認とは別で、同種失敗の再発時は実装・後続実行・コミットを停止し最初の証拠を保存する。期限延長・skip・製品合否条件の削除で通さない。2026-10-23の再チェックは9件×3回と全件1680 passedで充足。05-02-CHECKPOINT.md参照。

### 計画担当の裁量（上記確定回答を除く）

- トーストの表示時間・位置・見た目（既存 `pagefolio/toast.py` の ToastManager を基本に使う。Phase 4 の「既存 ToastManager をそのまま使えると仮定しない」に従い、起動直後の表示可否は計画で確認する）。
- 読込失敗の種別判定の実装方法（JSON デコードエラーと OSError の判別方法）。
- `_load_settings` / `_save_settings` の失敗を呼び出し側へ伝える API（戻り値・例外・状態フラグ等）。現状は両者とも例外を `logger.debug` で握りつぶしており、呼び出し元（`app.py`, `settings.py` 利用箇所の `dialogs/settings.py`, `dialogs/shortcuts.py`, `ocr_dialog.py`, `redact_ops.py`, `viewer.py`）はいずれも失敗を判定していない。
- 通知の内部データ構造（種別・文言キー・表示済みフラグ）。日英の文言キーは `pagefolio/CLAUDE.md` の規約に従う。
- D-14 の終了時保存抑止を、どの層（`_save_window_state` 側・`_save_settings` 側）で実現するかの方式。

</decisions>

## Existing Code Insights

### 現状の問題点（調査済み）

- `pagefolio/settings.py:254` `_load_settings()` — 例外を `logger.debug` で握りつぶし、既定値を返す。読込失敗が利用者に見えない（V110-CFG-01 の原因）。
- `pagefolio/settings.py:314` `_save_settings()` — `write-then-os.replace` の原子的書込み（WR-05）だが、例外を `logger.debug` で握りつぶす。失敗を呼び出し側が知る手段がない（V110-CFG-02 の原因）。書込失敗時に `.tmp` が残る可能性がある（D-12 の対象）。
- `pagefolio/app.py:149` — 起動時に `_load_settings()` を呼ぶ。画面構築前のため、通知は画面構築後に出す必要がある（V110-CFG-01 の「画面構築後」）。
- `pagefolio/app.py:585, 602, 636, 679, 693` 付近 — `_save_window_state`・`_toggle_lang`・`_reload_plugins` 等が `_save_settings` を呼ぶ。終了時保存（`_save_window_state`）は利用者の明示操作ではないため D-14 の対象。
- `_save_settings` の呼び出し元は `dialogs/settings.py:231`、`dialogs/shortcuts.py:283`、`ocr_dialog.py:1040`、`redact_ops.py:259`、`viewer.py:162, 183` にもある。

### 再利用可能な入口

- `pagefolio/toast.py` の ToastManager — 非モーダル通知の基盤。Phase 4 の文脈では「起動直後の表示に流用できると仮定しない」ので、計画で確認する。
- `pagefolio/app.py` の `_set_status()` — ヘッダーのステータス表示（D-01 系の補助表示として参照可）。
- `pagefolio/app.py` の `_rebuild_ui()` — 再構築時の通知保持（D-17）の接点。

### 維持する設計

- 設定の原子的書込み（write-then-os.replace）を維持する。
- 機密キーを保存対象から除外する `_SENSITIVE_KEYS` の扱いを変えない。
- 保存失敗時もメモリ上の `self.settings` を破壊しない（D-08）。

</code_context>
