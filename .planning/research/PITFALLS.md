# v1.10.0 の落とし穴調査

**対象:** Windows 11 向け Python/Tkinter PDF エディタの多重起動防止、既存画面復帰、設定失敗通知、PyInstaller 配布
**調査日:** 2026-10-21
**確度:** コード・既存テストの現状は高、未実装方式の失敗対策は中。Windows の前面化制限と旧版 EXE の制約は引き継ぎ済みの調査結果を採用。

## 重大な落とし穴

### 1. 排他取得前に Tk を作る／判定失敗を「未起動」とみなす

- **失敗・兆候:** 同時起動で編集窓が二つできる、または API 障害時だけ重複する。現行 `main()` は直接 Tk を作り、排他判定がない。[`pagefolio/__main__.py:19`](../../pagefolio/__main__.py#L19)
- **予防:** 窓・設定・PDF の初期化より前に、同一ログインセッションで共通の安定した識別名による排他を確定する。識別名に版番号・配置パス・Python/EXE 区別を入れない。取得失敗は「既存あり」と分けて利用者へ理由を示し、起動を止める（fail-closed）。ハンドルはアプリ生存中保持し、正常終了・初期化例外時に閉じる。強制終了時の回収は OS に委ねる。
- **検証／担当:** **Phase 4 起動制御**。排他 API を失敗注入して重複窓ゼロ、並列プロセス 2〜N 個でも所有者一つ、初期化例外・通常終了・強制終了後に再起動可能、ハンドル残留なし。版違い・別配置・`python pagefolio.py`・`python -m pagefolio`・配布 EXE を混ぜる。64-bit ctypes のハンドル型・エラー取得も単体検証する。根拠: [引継ぎ: 推奨仕様](../notes/GSD_HANDOFF_2026-10-21.md)、[CreateMutexW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexw)。

### 2. 2回目の起動が所有者へ届かない／通知だけで窓が見つからない

- **失敗・兆候:** 後続プロセスは終了したが最小化窓が戻らない、初期化中の要求が消える、OCR やモーダル表示中に Tk が固まる。Windows は前面化を拒む場合がある。
- **予防:** 排他判定と「既存画面へ復帰」の通信を別責務にする。所有者が受けた要求は準備完了まで保持し、重複要求は集約する。Tk ウィジェット・fitz 操作はメインスレッドの `root.after()` 側だけで行う。最小化解除を先に試み、OS が許すとき前面化する。拒否時はタスクバー等で気付ける手段を用意し、成功したふりをしない。後続側も通信不能と応答待ちを無限に続けず、理由を表示して終了する。
- **検証／担当:** **Phase 4 起動制御**。起動直後・最小化・別アプリにフォーカス・未保存編集・OCR 実行中・モーダル表示中に2回目を起動。窓数は一つ、既存 `doc`・Undo 履歴・OCR は不変、要求が最後まで処理される。前面化拒否を模擬し、復元と代替の注意喚起を確認。根拠: [`pagefolio/app.py:143`](../../pagefolio/app.py#L143)、[`pagefolio/app.py:498`](../../pagefolio/app.py#L498)、[Windows の SetForegroundWindow 制限](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)、[引継ぎ: 受入検証](../notes/GSD_HANDOFF_2026-10-21.md)。

### 3. 対応前の旧 EXE にも排他保証が及ぶと誤認する

- **失敗・兆候:** v1.10.0 と旧 EXE を並べると二窓になる。旧版は同じ排他名・復帰通信を実装していないため、後から相互排他を強制できない。
- **予防:** 保証文言を「本機構を搭載した版の相互起動は、版・配置・Python/EXE をまたいで同一セッション一つ」に限定する。非対応旧版との併用は対象外として配布・移行手順に明記し、旧版を強制終了したりプロセス名検索で無理に排除したりしない。
- **検証／担当:** **Phase 4 仕様・Phase 6 配布**。対応版同士の組み合わせ行列を実機で確認。旧版の試験は「保証外である」ことを確認し、誤った全版保証を文書に残さない。根拠: 現行起動経路に排他なし [`pagefolio/__main__.py:19`](../../pagefolio/__main__.py#L19)、採用範囲 [`PROJECT.md:10`](../PROJECT.md#L10)。

### 4. 設定エラーを既定値で隠し、後の保存で不正ファイルを上書きする

- **失敗・兆候:** 壊れた JSON・アクセス拒否時も既定値で起動し、設定が消えたように見える。現行 `_load_settings()` は例外を debug ログだけに残し、既定値を返す。`_save_settings()` も失敗を呼び元へ返さない。[`pagefolio/settings.py:254`](../../pagefolio/settings.py#L254)、[`pagefolio/settings.py:314`](../../pagefolio/settings.py#L314)
- **予防:** 「初回の設定ファイル不存在」は正常扱い。存在した設定の読込エラー・不正なトップレベル構造は区別して一度通知し、原因と対象パスを示す。失敗した原本を自動上書きしない。保存結果を呼び元へ伝え、一時ファイル書込失敗と `os.replace` 失敗を通知する。既存の機密キー除外を維持し、エラー文言・ログにキー値を出さない。
- **検証／担当:** **Phase 5 設定通知**。不存在・不正 JSON・妥当な JSON だが不正型・読込権限エラー、`.tmp` 書込不可・`os.replace` 失敗を注入。UI 通知の有無、原本バイト不変、機密値非露出、通知連打抑制を確認。現在のテストは既定値復帰・保存成功・例外の無送出と機密キー非保存まで。[`tests/test_utils.py:18`](../../tests/test_utils.py#L18)、[`tests/test_utils.py:395`](../../tests/test_utils.py#L395)、[`tests/test_settings_keyguard.py:65`](../../tests/test_settings_keyguard.py#L65)

### 5. 通知を早く出しすぎて消える／他の失敗通知を上書きする

- **失敗・兆候:** 起動時の設定読込警告が UI 構築前に失われる。既存 `ToastManager` は `_build_ui()` の末尾で作られ、異なるカテゴリの表示は一つを置換する。[`pagefolio/app.py:148`](../../pagefolio/app.py#L148)、[`pagefolio/ui_builder.py:187`](../../pagefolio/ui_builder.py#L187)、[`tests/test_toast.py:74`](../../tests/test_toast.py#L74)
- **予防:** 読込時は表示に必要な診断情報だけを蓄積し、UI 準備後にメインスレッドで通知する。設定保存の連続失敗は同カテゴリで集約し、保存できていない状態を見落とさせない。既存の保存・印刷失敗トーストと衝突させず、必要なら起動時はモーダルや永続的な表示を選ぶ。通知 UI の実装は既存スタイル・日本語/英語文言に合わせる。
- **検証／担当:** **Phase 5 設定通知**。起動時失敗、連続する保存失敗、既存 PDF 保存トーストとの競合、テーマ切替での UI 再構築を確認。既存テストはトーストの置換・更新・再生成と保存操作向けであり、設定通知の順序は未被覆。[`tests/test_toast.py:60`](../../tests/test_toast.py#L60)、[`tests/test_toast.py:171`](../../tests/test_toast.py#L171)

### 6. `--noconfirm` ビルドが唯一のサンプル原本を消す

- **失敗・兆候:** 配布先に `ocr_custom_prompt_sample.md` / `ocr_summary_prompt_sample.md` がなく、再ビルド前の内容を復元できない。現状、この二つは `dist/PageFolio/` のみ Git 管理で、ソース側に原本がない。[`docs/DEVELOPMENT.md:85`](../../docs/DEVELOPMENT.md#L85)
- **予防:** まず現存二ファイルの内容・ハッシュを保全し、配布出力から独立したソース原本を確定する。その後ビルド手順で原本を毎回コピーする。`--noconfirm` を使うのはこの保全とコピー手順の検証後。外部の編集用 `ocr_custom_prompt.md` / `ocr_summary_prompt.md` とサンプルを混同しない。
- **検証／担当:** **Phase 6 配布・リリース**。原本ハッシュと旧配布サンプルの一致、実際の `--noconfirm` 再ビルド後の二ファイルの存在・内容一致、配布 EXE 起動を確認。テスト中はユーザー編集済み外部プロンプト・設定を消さない。現行テストはプロンプト読込の優先順位とパス解決を検証するが、ビルド成果物は検証しない。[`tests/test_utils.py:261`](../../tests/test_utils.py#L261)、[`tests/test_prompt_templates.py:192`](../../tests/test_prompt_templates.py#L192)

## 見た目だけ完了する場合の受入チェック

| 項目 | 完了判定に必要な観測 | 担当案 |
|---|---|---|
| 排他 | 同時・連続起動でも窓と所有者が一つ。判定失敗は起動せず理由を表示。正常/強制終了後は再起動可 | Phase 4 |
| 復帰 | 最小化、OCR、モーダル、未保存編集中でも元の作業が残り、前面化拒否時も利用者が気付ける | Phase 4 |
| 設定 | 不存在は静かに既定値、破損/権限エラーは可視通知。保存失敗後も原本を保持し、機密値を出さない | Phase 5 |
| 配布 | 保全した原本から実ビルドし、二サンプルのハッシュ一致と EXE の起動を確認 | Phase 6 |

## 範囲と未決

- 起動時 PDF 引数の受け渡し、前回ファイル・閲覧位置復元、異常終了後の編集復旧、OCR 共通化、実 API UAT は今回の受入条件に入れない。[`PROJECT.md:17`](../PROJECT.md#L17)
- 復帰要求の通信方式、通知の持続・再試行 UI、配布原本の置き場は設計フェーズで決める。どの方式でも上記の失敗注入・Windows 実機・配布 EXE 検証を残す。
- 現行テストの被覆確認はコード読取に基づく。新機能の合否は実装後の `ruff check .`、`ruff format .`、構文確認、`pytest` と実機 UAT の結果で判断する。[`AGENTS.md`](../../AGENTS.md)
